# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Capturefab is an MIT-licensed Rust camera capture command-line tool for people, scripts and AI agents: one `capturefab` executable that lists, configures, captures from and records cameras, with a versioned JSON contract (`--json`, typed exit codes, `capturefab schema`). It implements GigE Vision, USB3 Vision and GenICam natively in Rust; webcams, RTSP/SRT/ONVIF streams, files and video encoding go through a bundled FFmpeg executable (not linked). JPEG and PNG stills are encoded in process (libjpeg-turbo, png, and Apple's JPEG engine through VideoToolbox on macOS), or on Linux by NVIDIA's nvJPEG or a VA-API driver in a helper process. Aravis is used only as an external test reference. There is no GUI, browser client, in-app assistant or update check.

## Vendor and native dependencies

Linking vendor SDKs and native libraries (camera SDKs, platform media frameworks, libusb, Aravis, GPU libraries loaded at run time such as CUDA/nvJPEG and libva) is permitted when it fits the repo's structure:
- Gate each one behind an optional Cargo feature so the default and `--no-default-features` builds keep working without it, and so `doctor` can report whether it was compiled in.
- Keep it in the process that uses it: camera SDKs belong in the per-camera worker (`session::run_worker`), never in the CLI client or the session coordinator.
- Isolate it in a separate helper process, the way FFmpeg is run, when its license cannot be combined with Capturefab's MIT code in release binaries (for example GPL), when it can crash, hang or leak and would take the camera worker down with it, or when it would bloat or complicate every build. Talk to helpers over bounded stdio JSON for control, and pipes or shared memory for pixels. The GPU JPEG encoders (nvJPEG, VA-API) are such: they run in `capturefab __jpeg-helper`, which the camera worker starts and which maps the frames' shared memory (`jpeg/helper.rs`).
- Check the vendor's redistribution terms before bundling its runtime, and add its notices to the release license output.

FFmpeg stays a separate executable. Never enable nonfree FFmpeg components: the bundled build is GPL, so a nonfree build could not be redistributed.

## Commands

```sh
cargo build                                           # default features: usb, jpeg, videotoolbox, nvjpeg, vaapi, keychain, shell
cargo build --no-default-features                     # CI checks it, and each feature alone
cargo test
cargo test --test capture                             # end-to-end binary tests (tests/*.rs, helpers in tests/support)
cargo test --lib <test_name> -- --exact
cargo test -- --ignored                               # FFmpeg media tests, once FFmpeg is available
CAPTUREFAB_BLESS=1 cargo test --test frame_golden     # rewrite tests/golden/frame.json after an intended change
cargo test --features copy-audit --test copies -- --nocapture   # where frames are copied, per frame, against the budgets
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --no-default-features -- -D warnings
cargo bench --bench runtime --no-default-features -- rgb/   # optional substring filters
python3 scripts/test-site.py                          # site, generated pages, installers, reference snapshot
python3 -m unittest discover -s scripts               # release, site and installer script tests
python3 scripts/site-reference.py --binary target/debug/capturefab   # after changing commands or result shapes
python3 scripts/test-media.py --binary target/debug/capturefab [--srt]  # needs MediaMTX on :18554/:18890
```

Use the simulator (`-c sim:0`, `sim:1`, `sim:line`, `sim:depth`, `sim:microscope`, `sim:thermal`, `sim:replay:PATH`) to exercise acquisition without hardware. Set `CAPTUREFAB_SESSION_DIR` and `CAPTUREFAB_CACHE_DIR` to isolated temp dirs when running the binary manually or in tests (tests set both for every binary they spawn; unit tests isolate themselves). The session dir must be private (mode 0700, as `mktemp -d` makes) or not exist yet: when its group or others have any access, commands that use a session (`--keep DUR`, `--session`, `--background`, `serve`, `session start|stop|status|list`) fail with `permission_denied` and a `chmod 700` hint, while the warm default falls back to a worker of the command's own. Three directories, found lazily by `dirs.rs` (`dirs::runtime`, `state`, `cache`; `dirs::scratch` and `temp` for short-lived files) as the first candidate that is or can be made private (0700, owned, not a symlink) and writable, so read-only and immutable hosts fall back to their tmpfs: runtime holds session descriptors, locks and other files needed only while processes run (`CAPTUREFAB_SESSION_DIR`, else `$XDG_RUNTIME_DIR/capturefab`, else a lingering Linux login's `/run/user/<uid>/capturefab`, else `~/.cache/capturefab/sessions`, else `/run/capturefab-0` for root on Linux, else `$TMPDIR/capturefab-<uid>`); state holds presets (`setups/`), the saved sign-in index, sessions' jobs and background session logs (`sessions/NAME.log`) (`CAPTUREFAB_STATE_DIR`, else `CAPTUREFAB_SESSION_DIR`, else `$XDG_STATE_HOME/capturefab` or `~/.local/state/capturefab` on Linux, the runtime dir's default elsewhere, else none); cache holds the extracted FFmpeg, encoder probes and GenICam XML (`xml/`) (`CAPTUREFAB_CACHE_DIR`, else the platform cache, else `<runtime>/cache`). A variable is used as given, with no fallback. A missing folder degrades one feature at a time: no runtime dir means no sessions (commands open their cameras alone), no state dir makes presets and sign-ins fail with `permission_denied` naming `CAPTUREFAB_STATE_DIR`, no cache turns caching off; `doctor --json` reports each under `folders`. `host.rs` reads the CPUs and memory the host and its cgroups leave (`cpus`, `threads` with the `CAPTUREFAB_THREADS` override, `memory_budget`), which size the encoder pool, FFmpeg threads and the burst queue. `media/bundled.rs` extracts the embedded FFmpeg once per user to the cache, else `<runtime>/cache`, else `$TMPDIR/capturefab-<uid>/cache` (noexec mounts skipped), shared across processes and trusted by a `verified` marker instead of re-hashing. `inspect` previews go to the private `<runtime>/inspect/` folder (0700, newest 64 files / 64 MiB). Settings a worker emulates for its camera (a simulator's registers, a webcam's video mode) are kept in `<runtime>/settings/` (`engine/emulated.rs`), so a `set` holds for later commands until the runtime dir is cleared, as a real camera keeps its settings until power-off.

FFmpeg: `build.rs` never builds FFmpeg. It embeds one (zlib-compressed, extracted to the cache dir on first use) from `CAPTUREFAB_FFMPEG_BINARY` when that is set at build time, in any profile, and otherwise in release builds only from `target/ffmpeg/<target>/bin/ffmpeg` when that exists; debug and test builds embed nothing, which keeps them small and quick to link. `CAPTUREFAB_FFMPEG_LICENSE` supplies the notice `licenses` prints. At runtime FFmpeg is `CAPTUREFAB_FFMPEG=/abs/path/ffmpeg`, else the embedded copy, else `ffmpeg` next to the executable, else `ffmpeg` on PATH (`doctor` reports which as `ffmpeg.source`); none of them is the typed `ffmpeg_missing` error with an install hint. Media tests requiring FFmpeg are `#[ignore]`d; run them with `CAPTUREFAB_FFMPEG` set and `-- --ignored`. `scripts/build-ffmpeg.sh` builds the pinned, checksummed GPL FFmpeg; `scripts/release.py` packages releases and refuses to build without it. On macOS `build.rs` links `assets/Info.plist` into the executable's `__info_plist` section (camera and local network usage strings); keep its `CFBundleIdentifier`, which existing camera permissions are stored under.

## Architecture

**CLI.** `main.rs` calls `lib::run`, which dispatches the hidden `__worker` argv to `session::run_worker`, `__jpeg-helper` to `jpeg::helper::run` (Unix, with the `nvjpeg` or `vaapi` feature) and everything else to `cli::main` (parse, then `cli::run`, then print and exit). `src/cli.rs` holds global flags, dispatch and routing; `src/cli/` has one module per command family (`camera` for list/info/features/get/set/exec, `capture`, `record`, `inspect`, `auto`, `preset`, `jobs`, `session`, `serve`, `login`, `onvif`, `network`, `doctor`, `debug`, `schema`, `watch` for live measurements, and `shell` with `shell/complete.rs` for the prompt and the line-per-command batch mode), plus `args` (camera selection, durations, times), `paths` (client-side path and template resolution: a path belongs to the caller even when a session does the work), `output` (the only place that prints results and errors), `signals`, and `term` (TTY detection, the status line a slow command shows, the camera picker and frames drawn inline for `--show`). The `shell` feature adds line editing, history and completion (rustyline); without it the shell reads plain lines. `controls.rs` parses feature names, banks (`TriggerMode[FrameStart]`) and the canonical controls (`exposure`, `gain`, `fps`, `roi`, `format`, `trigger`, `auto_exposure`, `auto_wb`). `naming.rs` renders output templates; `context.rs` holds capture tags.

**Process model.** Each camera runs in its own worker process (a re-exec of the same binary, overridable via `CAPTUREFAB_EXECUTABLE`) that leads a process group (Unix) or runs in a job object (Windows) with everything it starts. `session::SessionHandle` / `Coordinator` holds one `session/worker.rs` `Worker` per camera and speaks the protocol of `session/protocol.rs`: newline-delimited JSON requests on the worker's stdin; `hello`, then `accepted`, `started` (with a budget the hang watchdog counts from), events and `reply` lines on a private copy of its stdout, each with a sequence number. Frames never cross to the coordinator: the worker saves captures itself (`engine/saver.rs`, an encoder pool), measures inspections there (`engine/inspector.rs`) and writes an image captured to stdout to an inherited pipe (direct) or a private file in `<runtime>/out` (session). Inside the worker, `engine::WorkerHandle` runs one thread that exclusively owns the `camera::Camera` (and its transport), recordings and scheduled capture jobs (`scheduling.rs`); `engine/history.rs` checkpoints values so a preset apply or an auto change rolls back on failure (a multi-value `set` rolls back in `controls.rs`: what it wrote, in reverse, then any of the image geometry group, `controls::GEOMETRY`, that a write clamped or rescaled), `engine/lock.rs` takes the advisory camera lock, and `engine/saved.rs` reports saved files. Without a session, a command starts its own coordinator and worker in-process, so direct and session commands share one code path.

**Sessions and jobs.** `serve --name X` (foreground) and `session start` (a detached `serve`) run an `ipc::Server`: loopback TCP, token-authenticated, with a descriptor file in the private runtime dir. Clients send the same `SessionCommand`s through `ipc::call`. A camera command uses a session when `--session` names one or a running session holds the camera; otherwise it keeps its camera warm in the implicit `auto` session (started on demand, released after 60 s unused, `--keep DUR` to change it), and `--keep 0`, `CAPTUREFAB_KEEP=0` or `--no-session` give it a worker of its own, as does a host without a writable runtime dir. `--background` leaves a job running in a session. Long operations are jobs (`<session>-<n>`, `session/jobs.rs`), listed by `jobs`: a session saves its jobs in the state dir as they change, so `jobs` and `jobs wait` still answer for a session that has ended, and list a job its session died during as `lost`. The CLI waits on a job's changes with the session's `wait` request (`<seq>`-numbered, at most 25 s a call) rather than polling; `debug rpc` sends any `SessionCommand` (`{"op":...}`) by hand.

**Camera layers.** `types.rs` defines the `RegisterIo` and `Backend` traits (xml/start/next_frame/stop) and `types::Categorized`, the typed error category. Implementations live in `transport/` (`gige.rs` GVCP/GVSP, `usb.rs` U3V via `nusb` behind the `usb` feature, `simulator.rs` with `simulator/replay.rs`), while `media.rs` (+ `media/v4l2.rs`) provides FFmpeg-backed sources (host webcams, RTSP/SRT, files) and recording with encoder probing, including the Jetson GStreamer encoder. Decoders hand over frames in the format FFmpeg decodes to, as raw video whose format, range, matrix and size FFmpeg's info log line describes (`media/native.rs`; a layout Capturefab does not carry as decoded reopens the source for RGB24 PPM, as `sim:replay` always uses), and decode compressed live sources in hardware where a probe proved the method (`media/hwdec.rs`, `CAPTUREFAB_HWDEC`, with a per-source software fallback); under `auto` only a session's camera workers do (`session::served_session`), whose decoder runs on between commands. A Motion JPEG source is read as the JPEGs it sends (`-c:v copy -f mjpeg`; `media/mjpeg.rs` cuts them apart and decodes them with libjpeg-turbo into the layout FFmpeg would), each frame keeping its JPEG in `Frame::jpeg`, which a default-quality JPEG still stores as it is (`frame::encode_parts`, `passthrough`); a stream is found to be one on its first launch and opened again. A recording of an H.264/HEVC source copies its video instead of encoding frames (`media/copy.rs`, Unix): the decoder FFmpeg also writes what it reads as MPEG-TS to a pipe of its own, a `Tap` cuts it into frames and keeps those since the last key frame, and the recording's FFmpeg only remuxes them through the usual writer. GigE receive on Linux takes up to 32 datagrams a system call (`transport/gige/batch.rs`, `recvmmsg`), each predicted payload packet straight into its place; every message that did not land as predicted is copied out before any is taken in, since one put in its place could overwrite a later one's. Its socket buffer is forced past `rmem_max` where `CAP_NET_ADMIN` allows (`SO_RCVBUFFORCE`). On Linux the frame pipes to and from FFmpeg are enlarged to hold a frame (`media/pipes.rs`, `F_SETPIPE_SZ`, up to 1 MiB), and a frame's own bytes are `vmsplice`d into an encoder's pipe, the frame kept alive until FFmpeg has read it. `genicam.rs` parses GenICam XML (incl. zipped) into a feature node map evaluated live against `RegisterIo`. `camera.rs` ties discovery, backend and GenICam together; `camera_profile.rs` classifies area scan, line scan, depth, microscope and thermal cameras from what they advertise. `onvif.rs` does WS-Discovery and SOAP profile resolution to an RTSP URI. `network.rs` and `engine/network_defaults.rs` diagnose GigE paths and apply bandwidth sharing. `test_cameras/` holds unauthenticated GigE and ONVIF fakes for unit tests only.

**Frames and measurements.** `Frame.data` is a `framebuf::FrameBuf`: reference-counted and read-only, so the saver, inspections and a recording share the buffer the camera filled; nothing writes to a frozen buffer. Producers take buffers from the process's `framebuf::pool()` (at most 2 idle, at most 1/20 of `host::memory_budget`), whose recycled bytes are stale: only a producer that writes every byte it delivers may use `take_stale`, and unit tests poison every recycled buffer to catch one that does not. While a GPU JPEG engine is open (`framebuf::share`, held by its `jpeg::helper::Client`, its helper resting included), both pools hand out shared memory segments instead of heap vectors (`framebuf/shared.rs`: a sealed memfd on Linux, an unlinked POSIX shm object elsewhere; build cfg `jpeg_helper`), so the helper reads a frame where the camera wrote it; USB transfers keep heap vectors (`take_vec`). GigE receives payload packets straight into their frame (`Assembler::predict`/`landed`, vectored receive; `CAPTUREFAB_GVSP_SCATTER=0` copies as before); USB3 Vision takes a transfer's pooled buffer as the frame where one transfer holds a whole image (`Layout::whole`), else assembles by copying. Formats a consumer cannot read as they are are decoded a row at a time (`frame/rows.rs` `RowReader`: 8-bit gray or RGB exactly as `convert`, packed rows unpacked one at a time, a mosaic of any depth demosaicked from a ring of three 8-bit rows) straight into what reads them: a preview's box filter, a still's one buffer from `framebuf::transforms()` (a pool of its own, one idle buffer per encoder thread), a recording's scratch. `frame/view.rs` `FrameRef` is a frame or a region of one read in place, so inspections and auto exposure measure regions without cropping. Stills are `frame::encode_parts`: a body that borrows the frame where the format keeps its bytes (raw, Mono8 PGM, RGB8 PPM), plus one insert (PNM header, JPEG COM), written with vectored writes by `storage::save_parts` and stdout. JPEG goes through `jpeg/backend.rs` (`CAPTUREFAB_JPEG`): libjpeg-turbo encodes RGB8/BGR8/Mono8 in place, other color formats from JFIF Y'CbCr 4:2:0 planes written once from their rows (full-range planar 4:2:0 from its own planes), and its output stays in its own buffer; a hardware engine (on a thread of its own with deadlines to open and encode; a GPU engine's helper stops after a minute unused and starts again for the next frame) takes frames once checked against libjpeg-turbo for each size, format and quality (under `auto` on a thread of its own beside the first frame, which the CPU encodes; a check that finds it less faithful is repeated on later frames, a frame it declines goes to the CPU, and one that fails is turned off with a warning on stderr). `jpeg/videotoolbox.rs` runs in the worker and takes color frames, writing NV12 from the rows straight into its IOSurface and keeping the JPEG in its sample buffer. On Linux `jpeg/nvjpeg.rs` and `jpeg/vaapi.rs` run in `capturefab __jpeg-helper` (`jpeg/helper.rs`), started by the worker, which loads the vendor libraries with dlopen and gets each segment's descriptor once over its control socket (SCM_RIGHTS) and then one JSON line per frame naming the frame's segment and an output segment for the JPEG; a segment lent to it is not reused until it answers or has been reaped, and one that misses its deadline is killed. nvJPEG page-locks a frame's segment once and reads it in place (Jetson) or by one DMA, converting other formats once into page-locked JFIF planes; VA-API makes an aligned Mono8 frame's segment a USERPTR surface and writes other frames once into a derived image. Recordings hand FFmpeg a `media::Payload` of the shared frame, converting only what FFmpeg cannot read, once, on the writer thread; only RGB sources go to NVENC/AMF as RGB, a mosaic is demosaicked to RGB24 before any 4:2:0 encoder input (faster than swscale's direct path), FFV1 stores a mosaic as gray, and encoder probes are keyed by the input pixel format. Every copy site calls `copies::record` with its class (boundary, necessary, transform, avoidable); with the `copy-audit` feature a counting allocator and reports in `$CAPTUREFAB_COPY_REPORT` from each worker and GPU JPEG helper (`worker-PID.json`, `helper-PID.json`) back `tests/copies.rs`. `frame.rs` (with `frame/formats.rs` for the low-bit, signed, wide/planar/packed/alpha RGB, 565 and YUV/YCbCr layouts, including planar and semiplanar Y'CbCr with Capturefab's own custom-bit codes where PFNC has none) converts every common PFNC pixel format and encodes PNG (16-bit gray for monochrome wider than 8 bits, packed or not), PGM/PPM and raw; exposure, metering, clipping and focus read packed mono/Bayer and wide RGB samples where they lie, without a full-size intermediate image. `transport/gige.rs` normalizes continuous LSB packing to byte-aligned rows when the payload length shows it. The pixel-format table is in `docs/camera-compatibility.md`. `jpeg.rs` wraps libjpeg-turbo (`jpeg` feature); `videotoolbox` adds Apple's JPEG engine, `nvjpeg` and `vaapi` the GPU encoders (`CAPTUREFAB_CUDA_LIB_DIR`, `CAPTUREFAB_VAAPI_DEVICE`, which `media.rs` also gives an explicitly named `*_vaapi` FFmpeg encoder, one `record` never asks for; the VA-API helper keeps libva's messages for its errors, since the worker passes the helper's stderr on to the user). `inspect.rs` measures exposure, clipping and focus and renders the bounded preview; `auto.rs` runs the host auto-exposure loop. `tests/frame_golden.rs` pins their outputs against `tests/golden/frame.json`.

**Storage.** Captures and recordings go through `storage.rs`, never directly to disk: a still is written to a hidden `.NAME.<pid>-<rand>.partial`, synced and published by a rename that never replaces a file (`exists` otherwise, which naming answers with the next free name), a recording streams into a new file up to its size limit, and the folders a command published in are synced once at its end. No write takes a disk below its free-space floor (1% of the disk, 512 MiB to 20 GiB, or `CAPTUREFAB_MIN_FREE`; `0` turns it off): that is exit 6 `storage_full`. There is no ledger or budget. `volumes.rs` refuses writes under an unmounted mount point. `setup.rs` stores presets.

**Sign-ins.** `logins.rs`, `keychain.rs` (`keychain` feature) and `secret_input.rs` keep camera passwords in the OS credential store (service `capturefab-camera`), with a secret-free index in the state dir; the worker that opens the camera reads them. `scrub.rs` redacts secrets from every outgoing string.

## CLI contract

The CLI is a public, versioned automation contract (`capturefab schema`, `web/reference.html`, `web/agents.md`, `web/llms.txt`):
- `--json` prints exactly one single-line JSON document on stdout: the result on exit 0, `{"error":{"code","message","hint"?,"details"?}}` otherwise, also for usage errors. Results never contain a top-level `error` key; partial work of a failed command goes in `error.details`. Diagnostics go to stderr.
- The exit code is the category (0 ok, 1 failed, 2 usage, 3 unavailable, 4 timeout, 5 unsupported, 6 storage full, 130/143/129 interrupted); `error.code` is the specific reason. Both come from typed errors (`types::Categorized` plus reason), never from message text, and survive worker and session IPC hops.
- Keys are snake_case with units in names (`exposure_us`), no null values, RFC 3339 UTC times, bounded lists with `truncated`.
- Credentials in URLs must be redacted (`media::redact_url`, `scrub`) in output, logs and errors.

When changing commands or output shapes, run `python3 scripts/site-reference.py --binary target/debug/capturefab` (CI fails when `docs/cli-schema.json` differs from the binary), and keep `README.md`, `web/agents.md`, `web/llms.txt` and `web/docs.html` consistent; then `python3 scripts/docs-search.py`. Avoid publishing camera testing results or compatibility claims while the software is under rapid development.
