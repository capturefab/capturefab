A workbench for industrial cameras, webcams and streams

Capturefab finds GigE Vision, USB3 Vision, ONVIF, RTSP, SRT and host cameras, shows their live GenICam features, and captures, records or forwards from them. One self-contained binary is both the desktop app and the CLI. No vendor SDK, no Aravis, no Python.

Download Read the quickstart

Under rapid development. Camera support and behavior may change between releases. MIT licensed. Written in Rust. Source on GitHub.

Everything between the sensor and the file

The GigE Vision, USB3 Vision and GenICam stack is Capturefab's own Rust code. Webcams, network streams, decoding and encoding run through a bundled FFmpeg executable in its own process. Nothing else has to be installed.

What it connects to

GigE Vision
GVCP and GVSP with packet-size negotiation, packet resend and loss counters.
USB3 Vision
U3V over the operating system's USB stack: USB permissions on Linux, IOKit on macOS, WinUSB on Windows. No kernel driver of its own.
GenICam
Plain or zipped XML parsed into a live feature tree, with bounds, selectors, converters and access modes evaluated against the camera.
ONVIF, RTSP and SRT
WS-Discovery, profile resolution and authenticated SOAP. Credentials are redacted in logs, status output and the UI.
Webcams and capture cards
AVFoundation on macOS, V4L2 on Linux and DirectShow on Windows, including HDMI capture devices for a mirrorless camera.
Video files
Any file FFmpeg can decode behaves like a camera, which makes pipelines testable without hardware.

What it does

Capture
PNG, JPEG, raw, PGM or PPM frames now, after a delay, at a fixed time or on an interval. Schedules use explicit time zones and report progress.
Auto exposure and frame rate
Opt in per camera and pick a balance between image quality and frame rate. It prefers the camera's own auto functions, backs off on packet loss and can revert every change.
Record
MKV, MP4, TS or WebM through a bounded writer with a per-file size limit.
Forward
Publish to MediaMTX, an NVR or any RTSP, SRT, RTMP or UDP endpoint. Hardware encoders are probed before use, with a software fallback.
Save anywhere
Named folders, external drives and S3-compatible buckets, with a persistent upload queue that retries.
Many cameras at once
Sixteen cameras in one session by default, each streaming in its own process, in the app or headless.

What it promises

Never overwrites
An existing output file or bucket object is never replaced. A name collision is an error, not a silent loss.
Bounded storage
Captures and recordings share a budget, 10 GiB and 10,000 files by default. When it is full, Capturefab stops and says so instead of deleting anything.
Secrets stay out of files
Bucket credentials live in the OS keychain or the AWS credential chain. Stream URLs are redacted in logs, status and the UI.
Isolation per camera
A stalled or crashing camera cannot take another camera, the app or your script down with it.
Nothing phones home
No telemetry, no update checks, and this site runs no analytics.

How it works

Every camera gets its own operating-system process. Commands travel over a small pipe; frames never do.

Desktop app, CLI, scripts and agentsAll of them send the same commands. A script can attach to the window you already have open through a local, token-authenticated session, so you watch what it does.
CoordinatorOwns one child process per connected camera and talks to each one with newline-delimited JSON over its stdin and stdout.
One worker process per cameraExclusively owns the transport, the GenICam feature tree, scheduled jobs and forwarding.
  • GigE and USB3 Vision are handled in Rust, in this process.
  • Webcams, streams and encoders run in a bundled FFmpeg process beside it.
Shared-memory frame ring. Each worker writes frames into a three-slot ring that the app and CLI read directly. The newest frame always wins, so a slow consumer never builds up a backlog.

A headless session (capturefab serve --name bench) is the same thing without the window. Captures and recordings from any process go through one locked storage ledger, which is how the budget and the never-overwrite rule hold across processes.

Or build it yourself

Builds need a stable Rust toolchain, a C compiler and CMake, plus NASM on x86, because the JPEG encoder compiles libjpeg-turbo from source. Industrial cameras work without FFmpeg; webcams, streams and recording need a bundled or CAPTUREFAB_FFMPEG-supplied binary. The build guide covers both.

git clone https://github.com/capturefab/capturefab
cd capturefab
# desktop app and CLI
cargo build --release
# headless CLI
cargo build --release --no-default-features --features usb,jpeg
target/release/capturefab --camera sim:0 capture -o first.png

From nothing to a frame

Six steps, each one a command you can paste. Replace the camera address with one from discovery, or keep sim:0 and follow along without hardware.

  1. Open the workbench

    Run it with no arguments. It finds cameras on your network and USB ports, previews them, and shows their settings in the inspector.

    capturefab

  2. Find cameras

    Discovery covers GigE Vision, USB3 Vision and the simulator. Host cameras and ONVIF devices have their own listings. Add --json to any of them for structured results.

    capturefab discover
capturefab native            # webcams and capture cards
capturefab onvif discover    # IP cameras on the LAN

  3. Inspect and set features

    Pick a camera by discovered ID, serial number or IP address. Feature names come from the camera's own GenICam description, so list them first.

    capturefab --camera 192.168.1.10 features
capturefab --camera 192.168.1.10 get Width Height ExposureTime
capturefab --camera 192.168.1.10 set ExposureTime=5000 Gain=0

  4. Capture frames

    One frame to a file, ten to a folder, or a timelapse into a saved destination such as an external drive. Nothing is ever overwritten.

    Host cameras use a native locator instead of an address: avfoundation:0 on macOS, v4l2:/dev/video0 on Linux, dshow:video=Camera Name on Windows.

    capturefab --camera 192.168.1.10 capture -o frame.png
capturefab --camera 192.168.1.10 capture -n 10 -o frames
capturefab destination add-folder usb "/Volumes/CAMDISK/Capturefab"
capturefab --camera 192.168.1.10 capture --interval 10s -n 360 \
  -o timelapse --destination usb

  5. Record or forward

    Record to a bounded local file, or publish the camera to a server such as MediaMTX. Automatic encoder selection probes the hardware on this host and falls back to software.

    capturefab --camera 192.168.1.10 record -o clip.mkv --duration 30s
capturefab --camera 192.168.1.10 forward \
  --output rtsp://localhost:8554/camera \
  --encoder auto --fps 30 --bitrate 4M

  6. Hand it to a script

    Leave the app open and drive it from a terminal, a cron job or a coding agent. The commands are the same; the camera stays connected in the window.

    doctor reports what this host can do: compiled-in features, network interfaces, USB access and the JPEG and video encoders that passed a probe.

    capturefab sessions
capturefab --session gui connect 192.168.1.10
capturefab --session gui capture -n 10 -o frames --json
capturefab doctor --json

Built to be scripted

The CLI is a versioned contract. Results go to stdout as JSON, diagnostics go to stderr, and the exit code tells you what kind of thing went wrong before you parse anything.

$ capturefab --camera sim:0 get Width --json
{"ok":true,"result":{"features":[{"name":"Width","value":640}]},"version":1}

$ capturefab --camera 40123456 capture -o x.png --json
{"error":{"code":"unavailable","message":"camera '40123456' not found or ambiguous; run capturefab discover"},"ok":false,"version":1}
$ echo $?
3

Unix conventions. Pipes work: capture -o - --format raw streams a frame to stdout. Shell completions ship for bash, zsh, fish and PowerShell. serve runs a headless session with the same interface as the app.

Readable by agents. capturefab schema --json prints the full command and session contract for the installed binary. The site's agent instructions tell Claude Code, Codex, OpenCode and similar tools how to use an open session safely.

Questions people ask first

Do I need Aravis, a vendor SDK or FFmpeg installed?

No. GigE Vision, USB3 Vision and GenICam are implemented in Capturefab itself. Release binaries bundle FFmpeg for webcams, streams and encoding and run it as a separate process. You still need the operating system's own graphics, USB and camera drivers, and on Windows the WinUSB driver for USB3 Vision cameras.

Is it free to use commercially?

Yes. Capturefab is MIT licensed. The bundled FFmpeg executable is GPLv3 and is never linked into Capturefab; each release ships its complete corresponding source, build configuration and notices so that redistribution stays compliant.

Can a script control the window I already have open?

Yes. The app exposes a local session on the loopback interface, authenticated with a private token in your session directory. capturefab sessions lists it, and any command with --session NAME runs against it. Commands and their results appear in the app's activity log.

What happens when the disk fills up?

Capturefab stops the capture or recording and returns exit code 6 with a message that names the limit. It never deletes anything on its own. Retention that removes the oldest files is opt-in with --delete-oldest, and even then only files Capturefab created, whose checksum still matches, are candidates.

How do I verify a download?

Each asset in the release manifest has a SHA-256 checksum, and the download panel shows the matching command for your platform. Releases also carry GitHub build-provenance attestations: gh attestation verify FILE --repo capturefab/capturefab.

Why one process per camera?

Camera transports block, hang and occasionally crash, and vendor firmware is not always well behaved. Keeping each camera in its own process means a bad one cannot stall the app, the CLI or another camera, and the shared-memory frame ring keeps that isolation from costing throughput.
