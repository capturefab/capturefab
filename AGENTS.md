# Release work

When asked to release or fix a release candidate, carry the task through publication and verify the result. Read `docs/release.md` first. Use `python3 scripts/release-agent.py --help` for the release loop. Do not stop after merely starting a workflow and describe the release as complete.

1. Inspect the worktree and existing release run. Preserve unrelated edits. Put the intended stable version in `Cargo.toml` and `Cargo.lock`; candidates use Git tags `vVERSION-rc.N`, not a new Cargo version for each attempt.
2. Run checks appropriate to the changes. For release workflow edits, run `actionlint`, `python3 -m unittest discover -s scripts`, and `python3 scripts/test-site.py`. For Rust fixes, run the affected tests, formatting and strict Clippy. Never skip or weaken a failing check just to obtain a release.
3. Commit the intended changes. From a clean worktree, run `python3 scripts/release-agent.py start`. It allocates and pushes the next RC tag without moving existing tags. The tag push starts the Release workflow. If unrelated edits prevent a clean worktree, use an isolated worktree containing the intended committed release changes; do not stash or commit someone else's work.
4. Use `python3 scripts/release-agent.py status --commit SHA` until the tag run appears, then use `status --run RUN_ID` to follow that exact candidate. Poll with short waits and keep the user informed. Status is JSON and distinguishes validation, candidate failure, publication and a failure after publication.
5. On failure, run `python3 scripts/release-agent.py logs --run RUN_ID`. Inspect each failed job and its failed steps. Fix the root cause in source, build scripts or tests, reproduce it locally where possible, rerun relevant checks, commit the fix, and run `start` again for a new RC. Preserve failed draft releases and RC tags. If credentials or external infrastructure block progress, report the exact blocker; do not change signing policy, remove platform targets, or bypass validation.
6. Use `retry --run RUN_ID` only for a transient infrastructure failure on unchanged source. It reruns failed jobs on the same candidate; it does not include local fixes. It requires GitHub Actions write permission. Source fixes always get a new commit and RC tag.
7. Successful validation automatically promotes the original draft, creates the final version tag on the validated commit and publishes the same artifacts. Do not publish manually, move tags, or rebuild published versions. After promotion, verify the final release with `gh release view vVERSION --json tagName,isDraft,isPrerelease,url,assets,targetCommitish` and confirm the final tag points to the validated commit. Check the downloads update and Pages deployment when enabled. A site failure after publication requires repairing the site, not another binary release.

When the user has authorized releasing, routine fixes, checks, commits and new candidate attempts are part of that work. Report the final version, validated commit, release URL and any actual remaining limitation. Do not claim publication based only on a successful build or a queued run.
